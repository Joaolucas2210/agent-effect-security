# Contracts v1

These are provider-neutral data contracts, not runtime, authorization, tool-gateway, or evaluation-harness implementations. Every schema supports exactly `schema_version: "1.0"`; an unknown major (including `2.0`) is rejected. A future backward-compatible optional field increments the minor and adds fixtures; required or semantic changes require a new major and a separate reader/migration decision.

During H1 completion, `extensions` was added as an optional informational object to the original H1-01 schemas while retaining `1.0`: existing documents, producers, readers, JSONL and CSV remain valid because no producer emits it automatically. Consumers may ignore it. It never supplies required fields, changes normative interpretation, or grants permissions.

`null` means unknown or unmeasured. Numeric zero means measured zero. Unknown top-level and nested policy fields are rejected; additive informational metadata belongs only in `extensions`. All identifiers are non-empty, SHA-256 is lowercase 64 hexadecimal characters, timestamps are UTC RFC3339, and workspace paths reject absolute paths and traversal. Every pattern is anchored so that no identifier, hash, timestamp or path can carry a trailing newline and forge an extra line in a JSONL, CSV or log reader. Producers must store references rather than secret values, retrieved content, private reasoning, or credentials; schemas do not inspect string content to enforce that rule.

The seven contracts are `RunEvent`, `GateResult`, `TaskSpec`, `RunConfig`, `ContextItem`, `ToolCapability`, and `EvalResult`; this slice completes the four that the first one did not carry, and the normative oracles follow in the next. The contracts under test are read from `tests/scenarios.json`, so the matrix always covers exactly what is published. `EvalResult.gates` references the H1-01 `GateResult` schema, rather than copying it. Task text, context, and capabilities are untrusted data and never grant permissions; these schemas record requested/resolved data only.

## Security boundary

Schemas guarantee structural validation: closed top-level policy fields, required normative fields, and typed references. `extensions` is informational; it cannot replace required fields or override normative values. JSON Schema does not scan strings for secrets, authorize a `ToolCapability`, isolate execution, or enforce network, filesystem, or destructive-operation policy. Secret scanning, authorization, and isolation belong to the H2 Tool Gateway and H3 Runtime. Missing enforcement must be reported as deferred, never as active protection.

`contracts/v1/tests/normative-oracles.json` is a static, human-reviewed transcription of the approved Spec: field lists, nullability, enums, limits and closure per contract, each with its source document and section. The contract test compares it against the schemas and fails on any divergence. It is never generated from the schemas, and changing a schema requires changing the oracle in the same reviewed PR; the test reports how many of the seven contracts the oracle covers — all seven — and counts separately the schema values no approved document fixes, so an invented value stays visible instead of being rubber-stamped.

Run the fixtures with `python -m pip install -r ai-development-framework/requirements-test.txt` then `bash ai-development-framework/hooks/test-contracts-v1.sh`. The pinned Draft-07 `jsonschema` validator is mandatory for this self-test; a missing **or differently versioned** validator fails rather than producing a false green, because a different validator is a different gate. Point `ADF_CONTRACTS_PYTHON` at a virtualenv that has the pinned version if the system interpreter carries another one. CI installs the same file before quality gates. H1-01's writer remains validated by `test-run-events.sh`, and legacy JSONL/CSV readers and files are untouched.

For rollback, revert this PR (or remove only the oracle file and its comparison) in a reviewed PR; the pattern anchors are a security fix and should be reverted only with the reason recorded. Do not edit the H1-01 schemas, convert logs, or delete historical JSONL/CSV. Producers can continue emitting their prior contracts; no H1-02 producer is activated by this slice.
